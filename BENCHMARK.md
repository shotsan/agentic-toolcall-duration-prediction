# ToolDurBench: A Benchmark for Tool-Call Duration Prediction in Agentic LLM Serving

Goal: a reproducible benchmark to evaluate predictors of tool-call duration,
with Continuum's (arXiv 2511.02230) flat per-tool CDF as the reference baseline.
Designed so results can stand as a comparison point ("benchmark-grade").

## Why this benchmark exists
Continuum manages KV-cache retention with a TTL driven by `P(τ, f)` = empirical
CDF of past durations for tool `f`. For SWE-agents, Continuum sets `f` = the
FIRST WORD of the bash command (paper §, "we extract the string within the bash
block and use the first word afterwards as the tool call name"). This buckets
`cd src` with `cd /deep/tree`, and `python -c "1"` with `python train.py`.
We benchmark whether conditioning on the FULL CALL (command string / arguments)
predicts duration better, and whether that matters for scheduling (ranking).

## Fidelity to Continuum (what we match vs approximate)
MATCHED:
- Baseline = per-tool empirical-CDF, keyed EXACTLY as Continuum keys it
  (bash first word for SWE; function name for BFCL).
- Duration = wall-clock of the tool call (we measure real execution).
- Tool classes: coding-agent bash commands (SWE) + BFCL function calls.
- Metric family: error (APE) + we add tail + ranking (scheduling-relevant).
APPROXIMATED / DEVIATIONS (stated honestly):
- Continuum's traces (100 mini-swe-agent + 100 BFCL-WebSearch, GPT-5) are NOT
  yet open-sourced. We cannot replay their exact traces.
- Running mini-swe-agent end-to-end needs a paid LLM (GPT-5) + per-task Docker
  images (GB each) + hours. Out of scope for a single-box reproducible bench.
- Therefore we construct tool-call workloads from PUBLIC sources (SWE-bench_Lite
  task commands; BFCL executable functions) and MEASURE real durations locally
  on fixed hardware (i7-13700F). This isolates the PREDICTION question (given a
  tool call, how long will it take?) from the serving-system question.
- Network-bound tools (BFCL web search) are excluded from the compute-duration
  benchmark; their duration is external and only history-predictable. We note
  this is a genuine limit of code/arg conditioning, not a flaw in the method.

## Benchmark tracks
T1. BFCL-Compute (DONE, Exp #3): real BFCL MathAPI functions over list args of
    varying size. Tests hidden-runtime-argument conditioning.
T2. Shell-Commands (NEW): real bash commands an SWE-agent emits (cd, cat, ls,
    grep, find, wc, python -c, sort, head) over a real repo tree, with varying
    targets/sizes. Baseline keys on first word (Continuum-exact); ours keys on
    the full command (features of the command + target file size).
T3. (future) Full mini-swe-agent replay when Continuum traces are released.

## Metrics (report all)
- MAPE (mean abs % err), median APE (robust central tendency).
- Tail MAPE on slowest-20% (Continuum Fig 5: slow 10% cause up to 94% of delay).
- Spearman rho vs true duration (scheduling needs RANKING, not absolute time).
- Calibration (for distributional predictors): coverage of P50/P90 intervals.

## Models
PrETi-style robust set: per-tool CDF (baseline), Linear/Huber, RandomForest,
MLP, + Quantile GBM (distributional). Eval via K-fold / leave-one-out CV.

## Reproducibility
Fixed seed, fixed hardware (i7-13700F, documented in DESIGN.md §9), pinned
Python (sklearn 1.9). All scripts in this directory; data regenerated by
`make bench` (see Makefile).

## Results log

### T1 BFCL-Compute (see DESIGN.md §6c) — OURS WINS BIG
Real BFCL MathAPI over varying list sizes. 300 calls.
- per-tool CDF (Continuum): medAPE 93.8%, rho +0.06
- RandomForest (call-site/arg): medAPE 1.3%, rho +0.997
Duration ~ linear in list length (an argument the CDF ignores). Decisive win.

### T2 Shell-Commands (Continuum-exact first-word keying) — TIE / NO WIN
Real bash commands over the vLLM source tree (27k files). 400 calls, 0.6-46.6ms.
```
                             MAPE    medAPE  tailMAPE  rho
per-first-word CDF (Cont.)   40.9%   22.2%   31.3%    +0.50
RandomForest(full cmd)       42.4%   25.5%   23.4%    +0.53
QuantileGBM P50              40.9%   20.2%   25.4%    +0.57
QuantileGBM P90 coverage: target 90% -> actual 87.8% (near-calibrated)
```
HONEST FINDING: full-command features give ~no improvement here. These commands
are FAST (ms-scale) and dominated by process spawn + OS overhead, NOT by the
argument. A `cat` of 1KB vs 1MB barely differs vs the ~2ms fork/exec cost, so
the first word (which binary) already captures most signal -> CDF rho=0.50 is
already decent. Argument conditioning adds little when duration is
overhead-dominated.

### Cross-track conclusion (the benchmark's real contribution)
Code/argument conditioning beats the flat per-tool CDF **when duration is
argument/compute-dominated** (T1: heavy compute, big win) and **ties when
duration is overhead-dominated** (T2: fast shell commands). A per-tool CDF is a
surprisingly strong baseline for short, uniform calls. The predictor's value is
concentrated in the HEAVY tail of compute-bound tool calls — which, per
Continuum Fig 5, is also where scheduling delay concentrates (slow 10% of calls
= up to 94% of delay). So the method targets exactly the regime that matters,
but a benchmark must report that it is NOT a uniform win.

### Distributional prediction (next-step #3) — WORKS
Quantile GBM produces near-calibrated P90 upper bounds (87.8% vs 90% target),
usable directly as a TTL that rarely under-estimates. This is the robustness
property that answers "Beyond Prediction" (arXiv 2606.18431): feed a calibrated
interval to the TTL mechanism rather than a fragile point estimate.

### T2b Heavy Shell-Commands (compute-dominated) — OURS WINS, boundary confirmed
Real shell commands doing work ~ argument N (sort/grep/wc/awk/python over
seq N). 250 calls, 1.7-4292 ms (2500x range).
```
                             MAPE    medAPE  tailMAPE  rho
per-first-word CDF (Cont.)  156.6%   89.4%   87.2%    +0.47
RandomForest(full cmd)       73.5%    9.2%   28.8%    +0.90
QuantileGBM P50             146.7%    5.3%   14.3%    +0.86
QuantileGBM P90 coverage: target 90% -> 87.2%
```
CONFIRMS the T2 boundary claim: when duration is COMPUTE-dominated, full-command
conditioning crushes the flat CDF (medAPE 89.4% -> 5.3%; rho 0.47 -> 0.90). This
is precisely the heavy-tail regime that holds GPU KV-cache longest and dominates
scheduling delay. The fast commands where we tie (T2) barely occupy cache anyway.
